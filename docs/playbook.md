# 反射訓練台 · 移植手冊

把 BuzzCalculus 這一套搬到別的科目時該怎麼蓋、先蓋什麼、哪些東西可以直接抄、哪些必須重寫。

這份文件不是 BuzzCalculus 的規格（那在 `docs/spec/`），是**方法**。
寫給下一個科目的第一天。

---

## 0. 這套東西真正在賣什麼

不是題目。網路上到處都是題目。

賣的是**「這裡的答案是對的」這件事可以被證明**，而且是機器每天替你證明一次。

一個題庫產品的死法只有一種：使用者練了三十題，發現第三十一題的答案是錯的。
從那一刻起前面三十題也不算數了 —— 他沒辦法分辨哪些對哪些錯，
所以只能全部不信。這是不可逆的。

所以整套架構只服務一件事：

> **正確性必須是機器可檢查的，而且要擋在部署前面。**

其他所有決定（零後端、側表、kernel 分層、E2E）都是這條的推論。
如果某個設計讓「正確性」變成一件靠人記得檢查的事，那個設計就是錯的。

寫成一條可以貼在牆上的規則：

> 答案錯一題造成的信任損失，大於新增五十題的收益。

## 1. 移植順序

不要照「先做前端再做內容」的直覺。順序是反的。

### 第一步：先寫驗算器，再寫題目

**在題庫有第二題之前**，先回答這個問題：

> 給我一道題的題幹和一個答案，我能不能用一條**和解題無關**的路徑算出答案，再比對？

「和解題無關」是重點。不是把解法再寫一次 —— 那只是把同一個錯誤抄兩遍。

微積分的例子：
- 題目是 `∫₀¹ x²dx = 1/3` → 驗算器不去求反導數，直接跑高精度數值積分
- 題目是 `d/dx(x^x)` → 驗算器不做對數微分，直接對題幹做數值微分再跟答案比對
- 題目是隱函數 `x^y=y^x` 在 (2,4) 的 dy/dx → 驗算器不套 −F_x/F_y，
  而是在該點附近用牛頓法解出 y(x) 再數值微分

第三個例子最能說明「獨立」的意思：作者手推的代數錯了會被抓到，
因為驗算走的是完全不同的一條路。

**這一步做不出來的話，停下來。** 先想清楚這個科目的獨立路徑是什麼，
再決定要不要做。做不出來就代表你之後只能靠人工校對，
而人工校對在第三百題就會失效。

### 第二步：把驗算掛進 CI，不符必須是零

不是「跑起來看看」，是 `exit 1` 擋部署。
沒過驗算的題目不准進題庫，而不是「先上線再說」。

允許有「驗不了」的題目（證明題、定性題、觀念題），
但要跟「驗過了」分開統計，而且對外只講驗過的那個數字。

### 第三步：一次搞定的資料模型

題目物件只放**題目本身**：id / topic / 題幹 / 答案型別 / 答案 / 難度 / 解法 / 時限 / tags。

其他全部走側表（見 §2.2）。第一天就這樣做，之後省下的重構是幾週。

### 第四步：作答與判分

判分器要能接受**人類會寫的各種等價寫法**。這是靜悄悄流失使用者的地方：
答對了卻被判錯，比答錯還傷。

### 第五步：才輪到訓練循環

排程、弱點、難度自適應、每日任務。這些是產品，但沒有前四步就沒有地基。

## 2. 五根柱子

### 2.1 加層，不重寫

單體檔案長到一萬行之後，每次改動都有連帶風險，於是漸漸沒有人敢動它 ——
**而不敢動的產品會停在原地**。

作法是一次搬一塊出來，規則三條：

1. 純函式：不碰 DOM 查詢、不碰儲存、不讀 `Date.now()`
2. 主程式用**特徵偵測**接它，模組不在也要能跑（只是退回舊行為）
3. 行為完全不變，用 golden 測試釘住

```js
// 主程式端
function drawStrokes(canvas, ctx, strokes) {
  if (window.BuzzBoardRender && typeof window.BuzzBoardRender.paintAll === "function") {
    window.BuzzBoardRender.paintAll(canvas, ctx, strokes, options);
    return;
  }
  /* 原本的實作留在這裡當後備 */
}
```

**這條有一個致命的副作用，一定要先知道**：fallback 是安靜的。
它本來就該安靜（它是給模組壞掉時用的），
所以「模組沒載到」和「模組載到了」在畫面上長得一樣，只是結果不同。

實際發生過：作業本產生器用了不載 kernel 的那條路徑載題庫，
於是難度校準退回舊演算法，**整本 316 頁的難度徽章、章節排序、封面統計全錯**
（舊演算法把 29% 的題標成最高難度，正確答案是 5%），而且沒有任何東西會叫。

→ 所以要有一條 CI 規則：**產出給人看的東西的工具，不准走 fallback 那條路徑。**

### 2.2 側表（side tables）

所有後設資料放在「由 id 索引的產生檔」，不寫回題目物件。

```
src/kernel/uid_map.js         題號 ↔ 永久編號
src/kernel/rubric.js          難度三軸
src/kernel/origin.js          來源聲明
src/kernel/skill_tags.js      技巧標籤
src/kernel/derived_hints.js   機器推導的提示（每條帶可重驗的 claim）
src/kernel/verified_answers.js 通過獨立驗算的題目清單
src/kernel/equivalence.js     語意等價分組（抽題時去重用）
```

三個理由，重要性由高到低：

1. **改後設資料不會改變抽題結果。** 難度、標籤如果寫在題目物件裡，
   動一個欄位就可能改變隨機抽題的順序，golden 測試整片變紅，
   然後你會開始習慣性地按 `--update` —— 那等於沒有 golden 測試。
2. 產生器可以整份重跑，不必去 27 個題包裡逐一改。
3. 「作者寫的」和「機器算的」天然分開，畫面上才能誠實標示。

**規矩**：側表是產生的，也是 commit 的。改題庫之後所有產生器都要重跑，
而且 CI 要能發現「側表跟題庫對不上」。

### 2.3 自動產生的內容必須帶可重驗的 claim

這是唯一能接受的自動內容形式。

機器寫的提示不能是「先求反導數再代入上下限」—— 那句話對每一題定積分都成立，
也就是**對每一題都沒用**。要寫就寫這一題特有的事實：

- 「直接代入會得到 0/0」
- 「f(x)+f(π−x) 恆等於 2」（直接指向對稱性技巧）
- 「比值判別的極限是 1/3」

每一條都存一個 `claim`，CI 每次**重新算一次**。題目改了、事實不成立了，當場變紅。

```js
{ text: "比值判別的極限是 1/3", claim: { k: "ratio", v: 0.3333333 } }
```

人檢查不了六百條提示，機器可以，而且每次 CI 都會再檢查一次。

畫面上仍然要標明這是機器推的 —— 不要讓它看起來像有人背書。

### 2.4 CI 是唯一的品質來源

目前是 23 支驗證器 + 3 支 E2E + 4 道內容關卡，全部擋部署。

分成三類，缺一不可：

| 類別 | 測什麼 | 抓得到什麼 |
| --- | --- | --- |
| 驗證器 | 資料的自洽性 | 題號重複、標籤沒人認領、對外數字過期 |
| 內容關卡 | 答案本身 | 答案算錯、題目撞題、模板沒展開 |
| E2E | **看得到、點得到** | 結算頁全白、按鈕按不到、手機橫向溢出 |

第三類最容易被省略，也最容易漏掉真正的災難。
實際抓到過：結算頁 DOM 有兩萬字、畫面零字。字串比對全綠。

### 2.5 指標不准說謊

你自己看的數字和對外講的數字，都必須從真實資料算出來，而且被 CI 擋著。

這一條聽起來像潔癖，但它抓到的都是真問題：

- 關於頁寫「1,459 題、774 題通過驗算」，實際是 1,605 與 906 ——
  而那一頁整段的論點正是「這裡的數字可以相信」
- 內容深度報「作者寫的提示 830 題（51.7%）」，
  稽核之後真正題目專屬的是 333 題（20.7%）——
  其中 438 題的「第二條提示」是輸入格式說明（「請用 log(x) 這種寫法」），
  而那是要扣 6~18 分才看得到的

**指標說謊的代價是你會照著它做決策。** 以為缺口只有一半大，於是不補。

作法：對外頁面的每個會變動的數字掛標記，驗證器從真實資料重算比對。

```html
目前有 <strong data-claim="problems">1,605 題</strong>
```

「不符數 0」那一格要寫死成期望值，不是照實際填 ——
哪天它不是 0，驗證器就該紅，而不是默默把數字改大。

## 3. 換科目時：抄什麼、重寫什麼

### 可以直接抄（跟科目無關）

- 側表架構、產生器的形狀
- kernel 分層 + 特徵偵測 + golden 測試
- CI 的三層結構
- 難度三軸模型（見下）
- E2E 的骨架：主流程 / 手機版面 / 互動元件
- 對外數字的 claim 機制
- 提示的三層階梯與扣分模型
- 記錄合併（交換律 + 冪等）—— 這是之後要做跨裝置同步的地基，早點寫好

### 必須重寫（科目的核心）

**驗算器。** 這是整套東西唯一真正難的部分，也是唯一無法共用的部分。

各科的獨立路徑長什麼樣：

| 科目 | 獨立驗算路徑 | 可行性 |
| --- | --- | --- |
| 微積分 | 數值積分 / 微分 / 極限外推 / 級數求和 | 高，已驗證 906 題 |
| 物理 | 數值代入 + **因次分析**（因次不對直接判錯，這招極強） | 高 |
| 化學 | 化學計量、質量與電荷平衡、平衡常數回代 | 高 |
| 線性代數 | 隨機矩陣代入、行列式 / 特徵值數值計算 | 高 |
| 統計 | 蒙地卡羅模擬回推 | 中（要處理收斂與容差） |
| 程式設計 | 直接跑測資 | 高，最容易 |
| 生物 / 歷史 / 法律 | **沒有數值路徑** | 低 —— 見下 |

**沒有數值路徑的科目要誠實面對。** 不要假裝有。
替代方案是「兩個獨立來源同意」+ 逐題引用出處，
而且對外要講清楚品質保證的形式不同，不要用同一句話含混過去。
如果連這個都做不到，那這個科目不適合用這套打法。

### 難度三軸（跟科目無關，強烈建議照抄）

難度不要用一個數字憑感覺標。用三個獨立的軸：

- **步驟數**：要做幾個動作
- **冷僻度**：課本教不教
- **計算負擔**：算式有多重

理由：一題「用課本教過的方法但要算七步」跟一題「一步解決但要想到一個冷門技巧」，
難的地方完全不同。混成一個數字之後，系統就沒辦法幫使用者找出他真正卡在哪裡 ——
而那正是這種產品存在的理由。

三軸算出 R1–R6。**只改 rank 不改三軸是假的**，一定要從三軸重算。

## 4. 品質關卡清單

搬到新科目時，這張表照著蓋。標星號的是最容易被省略、但最會出事的。

**資料**
- [ ] 題號不重複、欄位型別正確、難度在範圍內
- [ ] 每個技巧標籤都被某個技巧節點認領（沒人認領＝這題對能力模型是隱形的）
- [ ] 側表跟題庫對得上（題數、id 全覆蓋）
- [ ] ★ 撞題偵測：正規化題幹之後比對整條與尾段（題庫越密撞得越兇）

**答案**
- [ ] ★ 獨立驗算，不符數必須是 0
- [ ] 判分器吃得下自己的參考答案（不然使用者答對會被判錯）
- [ ] ★ 提示裡不准出現完整答案（付分數買到答案 = 分數失去意義）
- [ ] 提示不准只是輸入格式說明

**呈現**
- [ ] ★ 數學式 / 化學式真的渲染一遍（渲染器通常設成不丟例外，壞掉只會變紅字，沒有東西會叫）
- [ ] ★ 對外頁面的每個數字跟真實資料一致
- [ ] 長題幹會折行，不是橫向捲動

**行為**
- [ ] E2E：開局 → 答題 → 結算 → 錯題進本
- [ ] ★ E2E：真的用手機視窗（390×844）量橫向溢出與觸控目標大小
- [ ] console 沒有錯誤、沒有 404

**隱私 / 法務**（如果打算收錢，這些不是可選的）
- [ ] 隱私政策的每一條承諾都有對應的自動化測試
- [ ] ★ 部署清單跟檢查清單一致（見 §5 第 2 條）

## 5. 十個踩過的坑

按「重複踩到的機率」排序。

**1. fallback 是安靜的**
模組沒載到不會報錯，只會用舊行為。整本作業本的難度標錯就是這樣來的。
→ 對「產出給人看的東西」的路徑加規則擋住。

**2. 檢查範圍比出貨範圍小**
法務頁通過了所有驗證器，卻沒被部署腳本複製上去。
商品頁新掛的兩支 script 沒進離線快取，因為驗證器只掃首頁。
→ 檢查的清單要**從出貨清單推導**，不要各寫一份。

**3. 測試沒有真的測到**
- 去重測試用 32 題的池子抽 20 題 —— 抽不到重複是運氣，不是功能
- 線寬測試門檻設 1.05，關掉功能後比值 1.08，照樣過
→ **每加一條斷言，就把對應的修正拿掉一次，確認它會變紅。**
這條規則今天抓到兩條假的測試。

**4. 門檻量錯了單位**
- 折行門檻看字串長度，但中文一個字佔兩欄 ——
  78 字元的題幹在畫面上是一條要橫拖的長條
- 「趨近 0」用絕對值 < 1e-6 判定，但 ln(1+3x) 在 h=1e-6 時值是 3e-6，
  看起來像「有限值」，實際上正以 h 的速度奔向 0
→ 量的東西要跟**使用者感受到的東西**同一個單位。

**5. 數值方法會在定義域邊界安靜地失敗**
極限引擎在目標點附近撒一圈取樣點外推，
函數的定義域邊界落在那圈外圍時（`ln(1+3x)` 撒到 x ≤ −1/3），整個外推變 NaN。
→ 靠近邊界要有貼身的小窗探測當後備，
但**不要為此放寬答案驗算那條路徑** —— 那等於拿答案的可信度換覆蓋率。

**6. 罐頭內容等於沒有內容**
「先判斷題型」對每一題都成立，也就是對每一題都沒用。
→ 用機械方法量：同一句話出現在 5 題以上就標記，
全部內容都是罐頭的題等於沒有專屬內容。這個數字要每次 CI 都看得見。

**7. 隨機抽樣的過濾器快照 bug**
先過濾候選再進迴圈，迴圈中加進 `used` 的項目不會被重新過濾。
id 唯一時看不出來，一旦引入「等價分組」就爆炸。
→ 迴圈內要重新檢查。

**8. CRLF**
Windows checkout 會把 LF 換成 CRLF，
於是寫死 `\n` 的正規式在本機永遠對不到，而 CI 在 Linux 上是 LF。
表現成「本機紅、CI 綠」，是最難查的一種。
→ 行尾一律寫 `\r?\n`。

**9. 工具鏈會吃掉反斜線**
（這一條跟環境有關，但值得記）某些 shell 的 heredoc 會把 `\\` 折成 `\`，
於是寫出去的 LaTeX 變成控制字元，錯誤訊息完全不指向真正的原因。
→ 含反斜線的檔案用檔案寫入工具，不要用 heredoc 或 sed。

**10. 假的「原價」**
劃掉一個從來沒賣過的價格，在台灣是有法律風險的。
→ 如果要標原價，CI 要擋住「原價不大於售價」以及「原價是憑空捏造的」。

## 6. 怎麼知道自己做對了

不是看題數。題數是最容易灌水的數字。

看這四個：

1. **通過獨立驗算的題數 / 總題數**，以及不符數是不是 0
   （BuzzCalculus：906 / 1,605，不符 0）
2. **題目專屬的提示覆蓋率**（不是「有提示的題數」——那會被罐頭灌爆）
   （BuzzCalculus：333 題題目專屬 + 295 題機器推導，合計 42.8%）
3. **CI 擋得住的東西有多少**，以及最近一次 CI 抓到的是什麼等級的問題
4. **對外講的每一個數字，是不是都有東西在擋**

第 2 項是目前最大的缺口，而且**沒有機器捷徑** ——
機器推導的天花板量過大約是缺口的 24%，剩下的是純人力。
這件事要早點知道，不要等到題庫有兩千題才發現提示要一條一條寫。

## 附：最小可行的第一週

如果只有一週，照這個順序，不要跳：

| 天 | 做什麼 | 產出 |
| --- | --- | --- |
| 1 | 想清楚這科的獨立驗算路徑，寫出驗算器骨架 | 能驗 10 題 |
| 2 | 資料模型 + 20 題種子 + 驗算掛進 CI | CI 綠、不符 0 |
